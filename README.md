# UI Test Automation Project (Practice Automation)

Проект автоматизированного UI-тестирования веб-приложения [Practice Automation](https://practice-automation.com/) в рамках дисциплины **«Автоматизация тестирования (Java, Python)»** (Куратор: **SimbirSoft**).

Проект разработан на **Python 3.12+** с использованием **Selenium WebDriver**, фреймворка **PyTest**, отчетов **Allure** и архитектурного паттерна **Page Object Model (POM)**.

## 🏗 Архитектура и структура проекта

Проект построен по паттерну **Page Object Model (POM)**, разделяя логику страниц (локаторы и методы взаимодействия) от самих проверок (тестовых сценариев):

```text
practice_automation_tests/
├── pages/                                # Page Objects (POM)
│   ├── __init__.py
│   ├── base_page.py                      # Базовый класс с явными ожиданиями и утилитами
│   ├── calendars_page.py                 # Page Object для /calendars/
│   ├── modals_page.py                    # Page Object для /modals/
│   ├── ads_page.py                       # Page Object для /ads/
│   └── form_fields_page.py               # Page Object для /form-fields/
├── tests/                                # Тестовые наборы (PyTest)
│   ├── __init__.py
│   ├── test_calendars.py                 # 14 тестов (10 позитивных, 4 негативных)
│   ├── test_modals.py                    # 14 тестов (10 позитивных, 4 негативных)
│   ├── test_ads.py                       # 10 тестов (7 позитивных, 3 негативных)
│   └── test_form_fields.py               # 14 тестов (10 позитивных, 4 негативных)
├── conftest.py                           # Фикстура WebDriver, авто-детекция браузеров, Allure-хуки скриншотов
├── pytest.ini                            # Конфигурация запуска тестов и маркеров
├── requirements.txt                      # Зависимости проекта
├── .gitignore                            # Исключения версионного контроля
└── README.md                             # Документация и сценарии тестирования
```

### Ключевые архитектурные решения:
- **`BasePage`**: инкапсулирует явные ожидания `WebDriverWait` и обработку исключений (включая автоматический скролл элементов в зону видимости и fallback через JavaScript Click при перекрытии элементов).
- **`conftest.py`**:
  - Поддержка запуска в режимах **headless** и **headful** (`--headless`, `--no-headless`).
  - Поддержка браузеров **Chrome**, **Edge** и **Firefox** с авто-определением доступного в системе браузера (`--browser auto/chrome/edge/firefox`).
  - Хук `pytest_runtest_makereport`, который автоматически перехватывает падения тестов и прикрепляет к отчёту Allure **скриншот экрана в момент ошибки** и **дамп HTML-кода страницы**.
- **Декораторы Allure**: каждый тест снабжен аннотациями `@allure.epic`, `@allure.feature`, `@allure.story`, `@allure.title`, `@allure.severity`, а действия разбиты на наглядные шаги `@allure.step`.

## 🎯 Особые требования ТЗ (п. 5 — Automation Tools)

> **Требование ТЗ:**
> *«На странице с формой поле Message заполнить следующим образом: получить средствами Selenium список элементов из раздела Automation Tools, преобразовать в текст и заполнить поле полученным списком через запятую.»*

**Реализация:**
1. В `FormFieldsPage.get_automation_tools_list()` выполняется поиск элементов списка:
   `//label[normalize-space(text())='Automation tools']/following-sibling::ul[1]/li`
   и извлечение их текстовых значений (`Selenium`, `Playwright`, `Cypress`, `Appium`, `Katalon Studio`).
2. В `FormFieldsPage.fill_message_with_automation_tools()` список преобразуется в строку через `", ".join(tools)`.
3. Поле `textarea#message` заполняется полученной строкой:
   `"Selenium, Playwright, Cypress, Appium, Katalon Studio"`.
4. В тесте `FP-08` проверяется совпадение значения поля `textarea#message` с ожидаемым списком через запятую.

## 📑 Подробное описание тестовых сценариев

Всего реализовано **52 теста** (37 позитивных и 15 негативных), что полностью перекрывает требование «7-10 позитивных и 3-5 негативных тестов на каждую страницу».

### 1. Страница «Календарь» (`/calendars/`)
#### Позитивные сценарии (10 шт.):
* **CP-01**: Проверка отображения ключевых элементов страницы (поле ввода даты, метка, подсказка формата `YYYY-MM-DD`, кнопка Submit).
* **CP-02**: Прямой ввод корректной даты в формате `YYYY-MM-DD` и проверка сохранения значения в поле.
* **CP-03**: Успешная отправка формы с сегодняшней датой и проверка появления сообщения *«Thank you for your response. ✨»*.
* **CP-04**: Успешная отправка формы с будущей датой (например, `2027-06-15`).
* **CP-05**: Успешная отправка формы с датой в прошлом (например, `2021-01-01`).
* **CP-06**: Проверка открытия всплывающего виджета jQuery UI Datepicker при клике на поле даты.
* **CP-07**: Выбор конкретного числа в интерактивном календаре виджета и проверка обновления поля даты.
* **CP-08**: Отправка формы с датой, выбранной через виджет календаря, и проверка успешного ответа.
* **CP-09**: Проверка возврата к форме ввода по клику на ссылку *«← Back»* после успешной отправки.
* **CP-10**: Проверка очистки поля ввода даты и повторного ввода нового значения.

#### Негативные сценарии (4 шт.):
* **CN-01**: Попытка отправки формы с пустым полем даты — проверка отсутствия сообщения об успехе.
* **CN-02**: Ввод буквенных/специальных символов вместо даты (`"not-a-valid-date"`) — отклонение некорректных данных.
* **CN-03**: Ввод даты в неверном формате (`DD/MM/YYYY`) — форма не принимает формат, отличный от `YYYY-MM-DD`.
* **CN-04**: Отправка формы со строкой из одних пробелов — отклонение ввода.

---

### 2. Страница «Модальные окна» (`/modals/`)
#### Позитивные сценарии (10 шт.):
* **MP-01**: Проверка наличия и видимости кнопок вызова модальных окон (*«Simple Modal»* и *«Form Modal»*).
* **MP-02**: Открытие простого модального окна (*Simple Modal*) по клику на кнопку.
* **MP-03**: Проверка заголовка (*«Simple Modal»*) и содержимого текста (*«Hi, I’m a simple modal.»*).
* **MP-04**: Закрытие простого модального окна кликом по кнопке-крестику (×) и проверка его исчезновения.
* **MP-05**: Закрытие простого модального окна нажатием клавиши `Escape`.
* **MP-06**: Открытие модального окна с формой (*Form Modal*) по клику на кнопку.
* **MP-07**: Проверка заголовка модального окна с формой (*«Modal Containing A Form»*).
* **MP-08**: Успешное заполнение полей формы (Name, Email, Message) внутри модального окна и подтверждение отправки.
* **MP-09**: Возврат к полям формы по клику на кнопку *«← Back»* после отправки внутри модального окна.
* **MP-10**: Закрытие модального окна с формой кликом по кнопке-крестику (×).

#### Негативные сценарии (4 шт.):
* **MN-01**: Отправка формы внутри модального окна без обязательного поля Name — форма не отправляется.
* **MN-02**: Отправка формы в модальном окне с пробелами в обязательном поле Name — валидация блокирует отправку.
* **MN-03**: Ввод некорректного адреса электронной почты (`invalid-email-format`) — форма не отправляется успешно.
* **MN-04**: Проверка активности оверлея (затемняющего слоя) при открытом модальном окне.

---

### 3. Страница «Рекламные окна» (`/ads/`)
#### Позитивные сценарии (7 шт.):
* **AP-01**: Проверка отображения описания и стартового текста страницы.
* **AP-02**: Автоматическое появление всплывающего рекламного модального окна по истечении таймера (задержка ~4.5 сек).
* **AP-03**: Проверка заголовка рекламного окна (*«Hi»*).
* **AP-04**: Проверка содержимого рекламного окна (*«I am an ad.»*).
* **AP-05**: Закрытие рекламного окна кликом по кнопке-крестику (×).
* **AP-06**: Проверка доступности основного контента страницы после закрытия рекламы.
* **AP-07**: Проверка полного скрытия оверлея рекламного окна после его закрытия.

#### Негативные сценарии (3 шт.):
* **AN-01**: Проверка отсутствия рекламного окна сразу в момент загрузки страницы (проверка работы таймера отложенного показа).
* **AN-02**: Проверка того, что закрытое рекламное окно не всплывает повторно само по себе.
* **AN-03**: Проверка недоступности кнопки закрытия рекламы, когда реклама скрыта.

---

### 4. Страница «Поля формы» (`/form-fields/`)
#### Позитивные сценарии (10 шт.):
* **FP-01**: Ввод текста в поля Name и Password, проверка сохранения значений.
* **FP-02**: Выбор одного чекбокса напитка (Coffee) и проверка флага `is_selected`.
* **FP-03**: Одновременный выбор нескольких чекбоксов напитков (Water, Milk, Ctrl-Alt-Delight).
* **FP-04**: Выбор радиокнопки любимого цвета (Red).
* **FP-05**: Проверка взаимоисключаемости радиокнопок (при выборе другого цвета предыдущий снимается).
* **FP-06**: Выбор значений из выпадающего списка «Do you like automation?» (Yes, No, Undecided).
* **FP-07**: Извлечение списка «Automation tools» средствами Selenium и сверка состава инструментов.
* **FP-08**: **(Требование п. 5 ТЗ)** Заполнение поля Message списком Automation Tools через запятую: `"Selenium, Playwright, Cypress, Appium, Katalon Studio"`.
* **FP-09**: Полное заполнение формы, нажатие Submit и перехват всплывающего JS Alert с текстом *«Message received!»*.
* **FP-10**: Проверка сброса (очистки) полей формы после подтверждения всплывающего алерта.

#### Негативные сценарии (4 шт.):
* **FN-01**: Попытка отправки формы без обязательного поля Name — проверка срабатывания HTML5-валидации.
* **FN-02**: Снятие отметки с ранее выбранного чекбокса (проверка функционала отмены выбора).
* **FN-03**: Попытка отправки полностью пустой формы — блокировка валидацией.
* **FN-04**: Проверка того, что начальное состояние выпадающего списка имеет пустое/дефолтное значение.

## 🛠 Требования и установка

### Системные требования:
- Python 3.12 или выше
- Браузер: Google Chrome, Microsoft Edge или Mozilla Firefox
- Git

### Установка зависимостей:
1. Склонируйте репозиторий или перейдите в каталог проекта:
   ```bash
   cd practice_automation_tests
   ```
2. Создайте и активируйте виртуальное окружение (рекомендуется):
   ```bash
   python -m venv venv
   # Windows (PowerShell):
   .\venv\Scripts\Activate.ps1
   # Linux/macOS:
   source venv/bin/activate
   ```
3. Установите зависимости:
   ```bash
   pip install -r requirements.txt
   ```

## 🚀 Запуск автотестов

### 1. Запуск всех тестов в headless-режиме (по умолчанию):
```bash
pytest
```

### 2. Запуск тестов для конкретной страницы:
```bash
# Только тесты страницы Calendars:
pytest tests/test_calendars.py

# Только тесты страницы Modals:
pytest tests/test_modals.py

# Только тесты страницы Ads:
pytest tests/test_ads.py

# Только тесты страницы Form Fields:
pytest tests/test_form_fields.py
```

### 3. Запуск по маркерам (позитивные / негативные):
```bash
# Только позитивные тесты:
pytest -m positive

# Только негативные тесты:
pytest -m negative
```

### 4. Запуск с отображением графического интерфейса браузера (Headful):
```bash
pytest --no-headless
```

### 5. Выбор конкретного браузера:
```bash
pytest --browser=chrome
pytest --browser=edge
pytest --browser=firefox
```

## 📊 Формирование и просмотр Allure-отчетов

Результаты прогона автоматически сохраняются в каталог `allure-results/`.

### 1. Просмотр отчета в браузере локально (требуется Allure CLI):
```bash
allure serve allure-results
```

### 2. Генерация статичного HTML-отчета:
```bash
allure generate allure-results -o allure-report --clean
allure open allure-report
```

В отчете Allure представлены:
- Иерархическое дерево тестов по Epics / Features / Stories;
- Подробный таймлайн и пошаговая детализация каждого шага `@allure.step`;
- Автоматически прикрепляемые скриншоты и дампы страницы при возникновении ошибок (`pytest_runtest_makereport`).
